# V67.3 Microphone Learning

The reported enrollment failure had an upstream input cause: telemetry showed an active training session at 0/5, Listening state, no device error, and RMS 0 from the system-selected virtual microphone. The user confirmed an unmoving meter and speech through a different headset. Previously saved name examples remained present. No speech recording, user-state modification or live-process restart was performed during diagnosis.

The name and command panels now contain the microphone selector and live input meter. The selector identifies the actual system-default device rather than displaying only an ambiguous System microphone label. Four seconds of an empty stream during active enrollment produces a device/mute hint. Startup, disconnected input, ordinary quiet listening and real low-level audio do not trigger that hint. This is a diagnostic only: endpointing, VAD, feature extraction and acceptance thresholds are unchanged, and silence cannot become an example.

Enrollment now exposes backend progress/rejection messages. Changing devices stops the current unfinished batch and explicitly asks the user to restart recording; already saved examples remain unchanged. Device choice continues through the existing HearingAction::SelectInput and hearing-state persistence, with no protocol or save-schema changes. The application does not silently pick or probe another microphone.

Validation scope: three HearingBridge tests pass (including empty-stream recovery and startup gating), fifteen care-menu tests pass, and five local audio input tests pass (including name enrollment through eight batches, sample conversion and silence rejection). A geometry test and native captures check that a long device label cannot widen the panel. The panel height adapts to available space and scrolls; the record/stop control precedes the progress messages. The first menu run encountered Windows AccessDenied recreating a temporary channel file; the recorded rerun uses a dedicated workspace temporary directory. The initial sandbox Clippy run could not access ancestor configuration directories; the final check runs with approved local build permissions. Both original logs are retained in the outer report.

Final release compilation and native captures use the same application/console source. The isolated GPU fixture covers name, no-input name, command and voice panels. Packaged binaries and source commit are hashed in the release manifest; the previous V67.2 package remains intact. This does not claim successful recognition of the user's headset audio: the user must select the intended device, verify a moving meter and record fresh examples. No raw microphone samples or copied hearing model are published.

Windows delivery is used on the user's current Windows host. No macOS package was built. Earlier release-sensitive physics tests are outside this narrowly targeted change; the V67.2 validation report records their baseline comparison.
