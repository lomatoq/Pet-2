# Независимая критика предложений развития мозга Pet2

Дата: 2026-09-08. Объект проверки: черновик `reports/PET2_BRAIN_RESEARCH.md`, предложения P0–P6. База аудита реализации: HEAD `6af2e42`. Проверка учитывает последующее уточнение P0 автором о namespace ID, разделении боли/аффекта и согласованном сбросе reward/eligibility; соответствующие рекомендации ниже уже частично приняты. Код и сам исследовательский документ в этой фазе не изменялись.

## Общий вердикт

Направление оправдано: причинный учёт действий, небольшое контекстное обучение, затем память и ограниченная модель тела. План реализуем без имитации полной биологии. Главный риск остаётся инженерным: система может успешно оптимизировать собственные метрики, не становясь полезнее пользователю. Поэтому необходимы два разных испытательных контура: воспроизводимость вычисления на записанной ленте и поведенческий результат в замкнутой среде, которая реагирует на действия питомца.

Принимаю последовательность «починить учёт → сильная простая база → небольшая добавка → проверка пользы». Предлагаю уточнения ниже до начала реализации. Здесь «изменить» означает сохранить направление и исправить условия реализации/приёмки; «отложить» — не включать в ближайший продуктовый этап.

| Предложение | Вердикт | Минимальное условие |
|---|---|---|
| P0: достоверность и общий runtime | Принять с обязательными уточнениями | Durable ID, финальное подтверждение исполнения, два вида replay, явный restart-контракт |
| P1: модель тела | Изменить | Предсказывать по доступной до перехода команде; проверять причинный вклад и качество неопределённости |
| P2: контекстные ответы | Принять с изменением награды | Не обучать успех из формулы собственных потребностей; заранее определить смысл результата |
| P3: рабочая/эпизодическая память | Изменить и разделить | Рабочая память раньше; долговременное извлечение после пользы P2; без двойного учёта того же опыта |
| P4: learning progress | Отложить до P1 и минимального P2 | Разделить внутреннюю validation и внешнюю оценку; исключить положительное смещение шумного прогресса |
| P5: replay во время отдыха | Принять для эксперимента после P0 и P1/P2 | Replay не наращивает статистическую уверенность бандита как независимые данные |
| P6: пластичность сетей | Отложить | Сначала диагностика и readout-baseline; затем одна проверяемая временная задача |

## P0 — принять, но сделать контракт конкретнее

**Что сильного.** Это обязательный фундамент, устраняющий C1–C4/C7–C9, а не дополнительная архитектура ради архитектуры. Вынесение runtime оправдано реальным отсутствием R12 в offline. Раздельные события, непрерывные наблюдения и модельные оценки — правильное решение.

**Что надо изменить.** `action_id` должен различать тип действия и уникальный экземпляр исполнения. Одного поля «выполненная команда после арбитража» мало: команда может быть ограничена phenotype, screen domain, физикой и не выполниться. Нужны proposal, admitted command и acknowledgement с фактической длительностью/долей выполнения, ограничениями и причиной отмены. В некоторых случаях результатом является правомерный no-op/отказ; это тоже определённый исход, но не неудача обучения.

Уникальность `event_id`/`episode_id` должна переживать перезапуск: persistently monotonic allocator либо `(session_id, sequence)`. На границе сохранения надо определить, что считается уже применённым: модель и watermark/ledger сохраняются согласованно. Иначе падение между сохранением веса и id повторно обучит событие либо потеряет его. Не нужен дорогой вечный журнал: достаточно ограниченного журнала/водяного знака и согласованного snapshot при упорядоченной доставке.

Один реальный исход законно может информировать несколько разных моделей. Требование «ровно один раз» относится к одной паре `(event, learner/update kind)` и к независимой статистике опыта. Запрещено суммировать несколько описаний одного исхода как независимые награды; не следует из этого запрещать, например, одному переходу обучать и предиктор тела, и политику по разным определённым правилам.

**Приёмка.** Добавить отказ после допуска, частичное исполнение, отмену до исполнения, смену контекста во время окна, первое событие после рестарта, повторную доставку вокруг сохранения, отсутствие frame/drop события при catch-up. C2 проверять ударом без жеста, а не только закрытым gesture episode: иначе монотонный negative может остаться незамеченным. Для C3 проверять, что novelty/habituation последнего жеста затухают, сохраняя запись для диагностики.

**Два контура.** Записанная сенсорная лента доказывает тождественность вычисления адаптеров. Она не доказывает полезность новой политики: если политика движется иначе, прежняя лента body/cursor-relative observations уже не соответствует её действию. Пользу измерять отдельно в общей замкнутой физике/сценарии. Для детерминизма задавать dt, порядок фаз, пропущенные кадры и RNG; не сводить общий runtime к одинаковому набору функций с различным расписанием.

**Реализуемость.** Разбить R13 на малые исправления C1/C2/C3/C9 с контрпримерными тестами, затем учёт/квитанции, затем общий step. Переписывание runtime не должно задерживать исправление уже доказанных знаковых/временных ошибок.

## P1 — изменить формулировку модели и тесты

**Что сильного.** Линейная модель, фиксированный горизонт, две простые базы и shadow mode — достаточный, ограниченный первый эксперимент. Объём 32×(8–12) параметров сам по себе не вызывает опасений по памяти.

**Причинная тонкость.** Предиктор получает только сведения, доступные до предсказываемого перехода: предыдущее состояние, допущенную итоговую моторную команду и известные внешние ограничения. Фактическое перемещение/исход являются target/acknowledgement, а не входом, который случайно попадёт в признаки при сборе «квитанции выполненного действия». Это особенно важно при разной частоте мозга и физики: сохранить точную границу t и t+Δt.

**Ограничение данных.** Пассивное наблюдение текущей политики может почти не различать эффекты команд. Перемешивание команд помогает выявить утечку/зависимость, но потеря качества после перемешивания ещё не доказывает причинность: команды коррелируют с состоянием. Добавить допустимые короткие контролируемые пробы либо парные ветвления физики из одинакового состояния с разными допустимыми командами. Не нужно исследовать всё пространство или мешать пользователю.

**Изменить приёмку.** Заранее определить полезные выходы и режимы: ошибка по скорости, контакту и деформации имеет разный масштаб. Нельзя объявлять победу средним MSE, если модель улучшила неподвижные кадры и ухудшила столкновения. Сравнивать по режимам и указывать достаточное количество информативных движущихся переходов. Требование превзойти физический baseline во всех режимах не обязательно: если простой физический прогноз лучше, его следует оставить. Новая модель нужна только там, где добавляет пользу.

Для управления нужна калибровка доверия: малое число примеров, смена материала/масштаба и выход за обученный диапазон должны уменьшать доверие. Добавить coverage/error versus confidence либо простой проверенный порог residual; высокий внутренний confidence сам по себе не критерий. Сначала один поведенческий эффект, например меньше бесполезных повторов при удержании без потери свободного движения. Без эффекта модель остаётся диагностической или удаляется.

## P2 — принять, ужесточить определение результата

**Что сильного.** 2–3 осмысленные стратегии одного взаимодействия — правильнее нового гигантского action space или косметических ±амплитуд. Законность молчания и отказа, фиксированные guards и контекстная проверка полезны.

**Основной риск награды.** Вычитание пассивного дрейфа недостаточно, если drives.update прямо уменьшает потребность на основании названия текущего действия. В таком случае policy выбирает действие, формула объявляет relief, и та же формула обучает policy, даже если тело ничего не выполнило. Нужно разделить расчёт состояния и внешнее свидетельство результата: подтверждённый отдых/реальное исполнение/явная реакция пользователя, а не одна запись current_action. Пассивный baseline фиксируется до эпизода из того же состояния на заданном горизонте и не подстраивается под желаемый исход. Он остаётся приближением, которое валидируется на контролируемых no-op/blocked-action опытах.

**Минимальная безопасная версия.** Начать обучение выбора ответов с явной оценки и хорошо определённого добровольного продолжения в ограниченном окне. Производные телесные затраты пока использовать для ограничений/контекста или отдельно валидируемой малой добавки. Не объединять все источники в единственную цифру, пока не описаны конфликт и приоритет: например, приятный контакт плюс явный отказ не должны дать положительный итог. Молчание — отсутствие наблюдения предпочтения, не автоматическое наказание; поздний явный ответ должен иметь понятную привязку либо не обучать никакой action.

**Приёмка.** Нужны замкнутый сценарий и заранее независимое правило outcome; противоположные контексты нельзя создать теми же формулами, которые получает learner в признаках. Сравнить результат, количество вмешательств, отмен и повторов; предпочтение редкого полезного действия не должно выглядеть хуже часто исполняемой слабой стратегии из-за частоты наблюдений. Проверить reward(-1), reward(0), blocked actuation и перезапуск посреди pending credit. Изменение вероятности выбранного варианта доказывает обучение, но полезность — только отложенные реальные/сценарные исходы при одинаковых ограничениях.

**Реализуемость.** Зависит от P0, не требует P1. Следует планировать ранний P2 как простую поведенческую базу для последующих дорогих компонентов.

## P3 — разделить рабочую память и долговременное извлечение

**Что сильного.** Ограниченная история переходов и низкая похожесть как «опыт отсутствует» устраняют соблазн превращать любой найденный эпизод в правило. Контрпример с одинаковым текущим кадром и разной предыдущей попыткой уместен.

**Изменение.** Маленькая рабочая память current goal/last attempt/refusal TTL может быть частью P0/P2: это детерминированное состояние эпизода, необходимое для нормального credit assignment. Её не нужно откладывать до обучения retrieval. Долговременное извлечение — отдельная добавка после P2.

**Двойной учёт.** Если P2 уже обучился на переходе, retrieval не должен повторно трактовать его как независимое свидетельство и разгонять уверенность. Пусть извлечение добавляет признаки/ограниченную поправку с измеряемым вкладом, а не скрытую вторую награду. Нормировку расстояния определить на обучающем наборе; отсутствие признака отличается от нуля; контексты разных материальных режимов/предпочтений пользователя должны иметь версию/возраст.

**Приёмка.** История действительно помогает только если исход зависит от истории; продемонстрировать это на новой ленте, не на точном запоминании учебных ключей. Сравнить P2 + простая one-step память и P2 + episodic retrieval. Если простой last-attempt флаг даёт весь эффект, сложное извлечение не оправдано. Добавить противоположные свежий/старый исходы, ложного соседа и смену нормировки. Срок отказа задаётся семантически: Focus действует пока включён, отказ текущему эпизоду — до его завершения; единый TTL для всех запретов неверен.

## P4 — отложить до качественного P1 и простого выбора P2

**Что сильного.** Измерять улучшение прогноза вместо голой ошибки и иметь «шумовой телевизор» в тестах — правильная защита.

**Проблема проверочной выборки.** Фиксированная validation, которая постоянно определяет бонус и выбор новых данных, становится частью адаптивного алгоритма. Её нельзя одновременно называть независимой конечной оценкой. Требуются внутренняя выборка оценки прогресса и отдельный внешний holdout; по мере смены режима внутреннюю выборку обновлять по явному правилу, сохраняя сопоставимость версий. Запретить обучение модели на внутренних validation-примерах, если метрика объявлена out-of-sample.

**Шумовой прогресс.** Оценка `max(0,error_old-error_new)` имеет положительное смещение даже при чистом шуме. Затухание без данных этого не устраняет. Учитывать знак/доверительный диапазон изменения, достаточное число примеров и стабильность по нескольким блокам. Пропуск известного контекста может вызвать забывание, а возврат — искусственный «прогресс»; проверить цикл забывание→переобучение как нежелательный источник бонуса.

**Приёмка.** Три сценария дополнить сменой режима, нерепрезентативной validation и редким полезным контекстом. Измерять не только доли выбора, но внешний навык/ошибку на новых переходах и бюджет вмешательств. Нулевой бонус при нехватке данных и сохранение существующих focus/attention budgets обязательны. Зависимость — P1 плюс проверенный механизм выбора; отдельный четвёртый владелец выбора действий не нужен.

## P5 — принять как ограниченный эксперимент, уточнить математику повторения

**Что сильного.** Разделение консолидации учёта и повторной оптимизации прямо исправляет C5. Равномерный baseline и равный compute budget — правильная проверка приоритетного replay.

**Скрытая повторная уверенность.** Недостаточно не увеличивать внешний `success_count`. В текущем Pet2 `ContextualBandit::update` уже делает SGD весов ([crates/lifecore/src/bandit.rs:81](/Users/darap/projects/Pet-2/crates/lifecore/src/bandit.rs:81)–`:84`), но одновременно увеличивает `attempts` и `total_updates` (`:86`–`:87`). Из них вычисляется `exploration_bonus` (`:69`–`:74`). Поэтому прямой многократный вызов update для одной записи меняет исследовательское поведение как будто получен новый опыт. Это не posterior/covariance модель; вводить новую математику ради исправления не нужно. Необходимо отделить weight optimization от учёта уникальных реальных исходов и использовать только последний в exploration_bonus. Допустима ограниченная SGD-оптимизация зафиксированного dataset с отдельным replay_steps; простейший первый P5 может повторять только примеры forward model P1.

**Off-policy и старый опыт.** Хранить контекст выбора, множество допустимых вариантов и при необходимости вероятность поведения, если алгоритм действительно требует importance weighting. Не вводить веса без математической необходимости. Стратегии из старой версии действий не переносить по совпавшему индексу; нужен schema/action-semantic version. При смене пользовательского предпочтения возраст и противоречащий свежий опыт должны ограничивать старое подкрепление.

**Приёмка.** Помимо счётчиков опыта сравнить attempts/total_updates, exploration_bonus и вероятность выбора после многократного сна без новых событий. Можно улучшить точность оптимизации, но нельзя заявить новые независимые подтверждения. Выигрыш приоритетного replay сравнить с равномерным и одним пересчётом на том же dataset, при одинаковом количестве обновлений/времени. Прерывание отдыха должно сохранять непротиворечивую модель; replay обновляет копию/версию и публикует согласованный результат между ticks, не частично во время исполнения.

## P6 — отложить изменение пластичности, принять диагностику сейчас

**Что сильного.** Не называть простое reward×trace e-prop, сначала обучаемый readout и ablation, а затем изменение одного пути — разумно.

**Уточнение задачи.** «Лучше удерживает временные зависимости» слишком общее. Выбрать конкретную delay/context задачу, которую P2 + рабочая память решают хуже, и показать заранее её ценность для питомца. Если простая память обеспечивает результат, усложнение сети не имеет доказанного преимущества.

**Критерии.** Finite и bounded weights — необходимые инварианты, но сеть может оставаться конечной и полностью молчать, насыщаться или повторять одну команду. Добавить распределение активности, разнообразие применённых действий, восстановление после нагрузки, forgetting при смене задачи и прямую метрику результата. Разные dt должны сравнивать одинаковое физическое время и сопоставимые входы; равное число ticks не является равным опытом. Статистически неподтверждённый выигрыш не оправдывает миграцию сети.

**Сохранение.** До эксперимента устранить C8: reward и eligibility должны иметь согласованную судьбу на restart. Для полного checkpoint сохранять временные состояния/RNG и версию; для обычного запуска последовательно очищать краткий credit. Нельзя сравнивать кандидатов, одному из которых достался старый reward на новые sensory traces.

## Бюджеты и окончательные критерии

Заявленные 0,5 мс p95 и 1 МиБ подходят как стартовые инженерные ограничения, не как обещания. Их необходимо определить точнее:

1. 0,5 мс — суммарное добавление всех включённых компонентов на один cognition tick на данном Mac после прогрева, а не отдельный бюджет для каждого. Указать p99/max, пропущенные сроки и влияние на frame/audio; редкие spikes могут быть невидимы p95.
2. 1 МиБ persistent state не ограничивает transient RAM, аллокации, trace-файлы, копии replay datasets и стоимость сериализации. Определить отдельно ограниченный RAM/запись на диск/retention; нормализованные признаки тоже не должны бесконечно логироваться.
3. Replay лимитировать CPU-временем/обновлениями на минуту и отменять/уменьшать при активности пользователя. Средние 20 Hz×0,5 мс ≈ 10 мс CPU/с не доказывают низкое энергопотребление: фоновые пробуждения, копирование и запись измеряются отдельно.
4. Offline сравнения бюджетировать по числу реальных переходов и суммарным обновлениям/времени. Равное число seed без равного опыта не даёт честной базы. Для online-обучения дополнительно сравнивать число вмешательств и отказов, а не только reward на удобных для модели эпизодах.
5. Минимальный полезный эффект, основной сценарий и допустимую регрессию определить перед запуском каждого эксперимента. Не нужен универсальный процент для всего проекта. Не продолжать увеличивать seeds до первого желаемого p-value: заранее определить расширение выборки/отдельное подтверждение.

## Минимальные изменения плана перед реализацией

- В P0 вписать persistent/session namespace ID, per-learner consumption и согласованность watermark с snapshot; явно добавить контрпримеры C1/C2/C3/C9.
- Разделить tape replay для воспроизводимости и closed-loop evaluation для пользы поведения.
- В P1 закрепить границу доступных признаков и запрет target leakage; простой физический прогноз оставить, если он лучше.
- P2 начать с независимых исходов; derived homeostatic reward не включать до no-op/blocked-action проверки пассивного baseline.
- Рабочую память отделить от retrieval, чтобы она помогала P0/P2 без преждевременной сложной памяти.
- В P4 добавить внешний holdout и контроль положительного смещения шумного прогресса.
- В P5 проверять не только счётчики, но и ложную statistical confidence, вызванную повторными observation updates.
- Уточнить общий compute/RAM/disk budget и заранее выбранный поведенческий критерий для каждого включения.

После этих уточнений план можно превращать в этапы реализации. Ближайший полезный результат для установленного приложения — исправленный учёт текущего опыта и контекстно уместный ответ на один вид взаимодействия. P4/P6 не должны задерживать эту доставку. При будущих изменениях кода действует проектное правило сборки, проверки и обновления обоих установленных macOS-приложений; сама эта исследовательская фаза установки не требует.
